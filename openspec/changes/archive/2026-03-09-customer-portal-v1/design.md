## 上下文

当前用户侧能力已经具备可复用的后端与前端基础，但入口分散在
`/console`、`/console/personal`、`/console/topup`、`/console/log`
与 `/pricing` 等多个页面中。客户需要跨多个页面理解自己的登录方式、
余额、订阅、消耗、日志与模型信息，整体体验更像后台功能集合，而不是
面向付费客户的产品化门户。

本次设计面向一个全新的客户门户 v1，目标是在不推翻现有后端契约的前提下，
把现有能力重组成一套独立、简约、时尚且正规的客户界面。v1 以复用现有
接口和前端数据逻辑为主，优先完成信息架构、路由分层、统一壳层、统一筛选
和关键页面重构。

约束条件：

- 必须保留现有管理后台能力，不与客户门户混用导航与语义。
- 必须优先复用现有接口 `/api/user/*`、`/api/subscription/*`、
  `/api/log/*`、`/api/data/self` 与 `/api/pricing`。
- 必须兼顾桌面端与移动端，避免只针对宽屏设计。
- 必须延续现有国际化与 Semi UI 体系，不引入对 v1 非必要的新依赖。

## 目标 / 非目标

**目标：**

- 建立独立的客户门户命名空间与统一导航壳层。
- 提供统一认证中心，整合邮箱密码、OAuth、Passkey 与 2FA。
- 提供客户总览、数据分析、钱包与订阅中心、日志中心、模型广场。
- 通过统一的卡片、筛选器、详情抽屉与主题变量形成高级感一致体验。
- 在 v1 中尽量复用现有后端接口与现有前端 hook，降低交付风险。

**非目标：**

- 不重写管理后台，也不把管理后台页面直接改造成客户门户。
- 不在 v1 内重构后端计费、订阅、日志或认证核心逻辑。
- 不强制新增聚合 API；若需要额外聚合能力，作为后续增强处理。
- 不在 v1 内引入复杂的可视化编辑器、运营工作台或管理员功能。

## 决策

### 决策 1：客户门户使用独立路由命名空间与专属壳层

采用独立的 `/app/*` 命名空间承载客户门户，并建立专属 `PortalShell`
组织左侧导航、顶部状态栏、内容容器和移动端适配。

选择原因：

- 可以从根本上把客户体验与管理后台分层。
- 可以逐步迁移现有用户页能力，而不影响现有 `/console/*`。
- 更适合后续继续演进门户导航、角色入口和深链接。

备选方案：

- 继续扩展 `/console/*`：实现成本较低，但会进一步混淆客户与管理员语义。
- 直接覆盖现有客户页：迁移风险较高，也不利于灰度切换。

### 决策 2：v1 优先复用现有接口与数据 hook，而不是先新增聚合 API

客户总览、账单中心、日志中心与模型广场优先复用现有接口和 hook，必要时
在页面层做组合与适配，不把新的后端汇总接口作为 v1 前置依赖。

选择原因：

- 现有接口已经覆盖登录、用户信息、订阅、充值、日志、统计和定价目录。
- 复用现有数据层可以缩短首版交付周期，降低跨层改动风险。
- 可以先验证客户门户 IA 与体验设计，再判断是否值得新增聚合接口。

备选方案：

- 先做统一 summary API：首屏更简洁，但需要新增后端契约和更多联调成本。

### 决策 3：认证中心与门户壳层解耦

认证中心单独负责未登录态体验、登录方式选择、2FA 二段验证与登录后回跳；
门户壳层只负责已登录态页面结构，不承载登录流程细节。

选择原因：

- 登录态与已登录态的信息密度和交互模式完全不同。
- 认证流程独立后，可以更清晰地处理 Passkey、OAuth 和 2FA 分支。
- 有利于控制受保护页面跳转与回跳逻辑。

备选方案：

- 把登录页嵌入门户壳层：结构不清晰，也容易造成导航和权限混乱。

### 决策 4：跨页面使用统一筛选器与统一详情抽屉

总览、分析、日志与模型广场之间共享统一的时间、模型、分组等筛选语义，
并尽量复用统一详情抽屉或侧边面板承载日志详情、模型详情与账单上下文。

选择原因：

- 能让客户快速理解不同页面之间的关系。
- 可以显著降低多页面风格和交互不一致的问题。
- 更容易实现“从总览跳日志”“从模型跳日志”之类联动体验。

备选方案：

- 每个页面独立设计筛选器和详情弹层：短期更快，但长期一致性较差。

### 决策 5：视觉系统采用高级 SaaS 风格，但不引入重型设计依赖

v1 采用暗色高级感、冷灰主色、克制强调色、大留白、细边框与统一卡片层级，
通过主题变量与局部组件重构完成风格升级，不引入额外的大型 UI 框架。

选择原因：

- 仓库已有 Semi UI 和现成的前端组件体系，继续复用更稳妥。
- 视觉升级的关键在于壳层、层级、间距、卡片与图表编排，而不是换整套框架。
- 有利于保持现有国际化、主题与组件资产兼容。

备选方案：

- 引入新 UI 框架：视觉自由度更高，但会显著放大迁移成本与一致性风险。

### 决策 6：v1 页面结构围绕“总览 → 交易 → 追踪 → 决策”组织

页面层次建议固定为：

- `/app/overview`：总览首页
- `/app/analytics`：数据分析
- `/app/wallet`：钱包与额度
- `/app/subscription`：我的订阅
- `/app/logs`：日志中心
- `/app/models`：模型广场
- `/app/account`：账户与安全

选择原因：

- 这套分组能覆盖客户从“看状态”到“做决策”的连续路径。
- 与当前已有能力一一映射，便于从现有页面迁移内容。
- 能让左侧导航结构保持稳定，利于长期扩展。

备选方案：

- 继续保持个人中心、充值、日志、定价各自独立入口：学习成本高，缺少产品化叙事。

## 风险 / 权衡

- **现有客户功能分散在多个旧页面中** → 先构建门户壳层与新路由，再逐步迁移
  具体内容，避免一次性替换全部入口。
- **首屏需要多接口组合，可能影响加载体验** → v1 先通过骨架屏、分区加载与懒加载
  控制体验；若仍不足，再新增聚合接口。
- **日志、模型、账单之间的联动复杂度较高** → 统一筛选条件命名和页面跳转参数，
  先保证最关键的跨页路径。
- **视觉升级容易演变成大规模样式重写** → 优先改壳层、主题变量、关键卡片与详情
  组件，限制 v1 的样式改动范围。
- **移动端体验容易滞后于桌面端** → 在路由与壳层设计阶段同步规划移动端导航和
  内容折叠方式，不把移动端延后到最后处理。

## 迁移计划

1. 新建 `PortalShell` 与 `/app/*` 路由，不影响现有 `/console/*`。
2. 先迁移认证入口与客户总览页，建立新门户的首个完整路径。
3. 逐步迁移钱包与订阅、日志中心、模型广场。
4. 保留旧入口作为兼容路径，直到新门户关键流程验证完成。
5. 在确认新门户稳定后，再评估是否将旧用户入口重定向到新门户。

回滚策略：

- 若新门户出现问题，可直接继续使用现有 `/console`、`/console/topup`、
  `/console/log` 与 `/pricing` 等旧入口。
- 因 v1 不强依赖后端契约变化，回滚主要是前端路由与入口回退，风险可控。

## Open Questions

- v1 是否需要首屏聚合 API，还是先完全接受多接口拼装的加载模型。
- 模型广场中的“个人使用视角”是否仅展示最近使用与消耗，还是需要更深入的
  模型级分析图表。
- 客户门户是否需要在 v1 中提供帮助中心、工单入口或通知中心。
- 新门户完成后，旧的客户侧入口是长期保留还是在后续版本统一收敛。

## 第七阶段校验与 API 评估

### 视觉一致性收口

第七阶段通过共享主题变量、统一详情面板样式和统一状态块，收口了
总览、分析、钱包、订阅、日志与模型广场的视觉层级。重点包括：

- 抽取门户级主题变量，统一卡片圆角、边框、阴影与文本层级。
- 引入共享 `PortalStateBlock`，统一加载态、空态与错误态表达。
- 为账单、日志与模型侧栏补充统一详情面板样式，减少页面之间的观感漂移。
- 强化移动端下的按钮铺满、筛选器换行和关键面板堆叠规则。

### 验证结论

本阶段以前端 best-effort 方式完成校验。仓库当前缺少
`.trellis/spec/frontend/index.md`，因此无法按约定读取 Trellis
前端规范，也没有执行视觉回归类自动化脚本；当前结论基于代码审查、
路由接线核对与生产构建验证。

已完成的验证范围：

- 登录与门户入口：认证中心、登录后回跳、`/app/*` 门户壳层接线。
- 桌面端关键路径：总览、分析、钱包、订阅、日志、模型广场的布局和共享样式。
- 移动端关键路径：门户壳层侧栏、总览主按钮、时间筛选条、账单与日志侧栏、
  模型广场按钮区的响应式规则。
- 构建级验证：使用 `pnpm run build` 完成前端生产构建，确认第七阶段改动可参与构建。

### API 评估

当前 v1 仍然可以继续基于现有接口推进，不需要把新聚合 API 作为发布前置条件。
原因如下：

- 客户总览、钱包、订阅、日志与模型广场的核心数据均已能通过现有接口组合得到。
- 第七阶段的主要问题在于视觉一致性和状态表达，而不是数据无法取得。
- 继续复用现有 hook，能保持 v1 的实现边界稳定，避免新增跨层联调风险。

但从后续体验和性能角度，建议把下列接口列为 v1 后的增强项：

1. **客户总览聚合 API**
   - 目的：压缩总览首屏的多接口并发数量，减少首屏等待和状态拼装复杂度。
   - 适用时机：当总览页继续增加经营洞察、预警和账单摘要时。

2. **个人模型分析聚合 API**
   - 目的：直接返回个人高频模型、高消耗模型、趋势摘要与推荐对比数据。
   - 适用时机：当模型广场需要更深的“我的使用分析”而不再满足于页面层拼装时。

结论：第七阶段后，`customer-portal-v1` 可继续沿用当前 API 进入后续收尾与归档；
新增聚合 API 不是阻塞项，而是性能和体验优化项。
