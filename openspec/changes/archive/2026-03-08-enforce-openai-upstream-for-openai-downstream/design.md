## 上下文

当前运行时的渠道选择主要按分组、模型、优先级和权重进行，协议兼容性并不是候选过滤条件。与此同时，部分非 OpenAI 上游渠道会被视为支持 OpenAI 风格端点，因此 OpenAI 下游请求可能先命中非 OpenAI 上游渠道，再由 adaptor 做协议转换。

这让管理员无法用一个明确的系统开关表达“OpenAI 下游请求不要做协议转换”的意图，也让路由行为和最终上游协议之间缺少一条显式约束。

## 目标/非目标

**目标：**
- 为 OpenAI 风格下游请求新增一个系统级严格模式开关。
- 在开关开启时，只允许 OpenAI 风格下游请求选择 OpenAI/Codex 上游渠道。
- 在渠道选择阶段完成过滤，而不是等到适配转换阶段才发现不兼容。
- 在管理端暴露该开关，并通过定向验证锁定行为。

**非目标：**
- 不实现“每个渠道支持哪些下游协议”的独立能力矩阵。
- 不重构现有 endpoint 推导、模型映射或 adaptor 转换框架。
- 不改变非 OpenAI 下游协议（如 Claude、Gemini、Rerank、Embedding）的现有选路逻辑。

## 决策

### 决策1: 采用系统级布尔开关，而不是每渠道能力声明

当前仓库已经有 `global.*` 全局模型设置入口，适合承载一次最小、可落地的策略控制。先使用布尔开关可以在不扩展渠道管理数据结构和前端复杂表单的前提下，直接解决“禁止 OpenAI 下游协议转换”的核心问题。

后续如果需要更精细的能力控制，再扩展为每渠道支持的下游协议白名单会更自然，但这不属于本次 onboarding 的范围。

### 决策2: 用共享兼容性判断封装“下游协议 × 上游协议”的限制

本次变更会围绕 OpenAI 风格下游请求建立一个明确的兼容性判断：

- 下游为 `chat/completions`、`responses` 或 `responses/compact`
- 且严格模式开启
- 则只允许 `APITypeOpenAI` 或 `APITypeCodex`

这样可以把规则集中在一处，避免在运行时选路和渠道测试里各自写一套分支判断。

### 决策3: 把限制加在渠道选择阶段

限制应尽量发生在“候选渠道筛选”阶段，而不是选中渠道后再报错。这样做有三个好处：

- 不兼容渠道不会参与优先级和权重竞争
- 错误边界更清晰，路由行为更符合管理员预期
- 将来若扩展为更细粒度的协议能力矩阵，可以沿用同一过滤入口
