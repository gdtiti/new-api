# customer-logs-center 规范

## 目的
定义客户门户的统一日志中心：在同一入口下查询 API 日志、任务日志与图像相关
日志，支持统一筛选条件、详情展示，并允许从总览/模型等页面带筛选参数跳转。

## 需求
### 需求: 统一客户日志入口
客户门户必须为用户提供统一的日志中心，覆盖 API 日志、任务日志与图像
相关日志，并且禁止要求用户理解后台内部模块划分才能完成查询。

#### 场景: 用户进入日志中心
- **当** 用户进入客户日志中心
- **那么** 系统必须提供 API、任务与图像日志等统一入口
- **并且** 使用一致的导航与页面结构

#### 场景: 用户切换日志类型
- **当** 用户在不同日志类型之间切换
- **那么** 系统必须保留统一的筛选框架与展示风格
- **并且** 不把不同日志类型拆成完全割裂的体验

### 需求: 统一筛选行为
客户门户必须支持按时间、模型、分组、请求 ID 与状态筛选日志，并且
同名筛选项在不同日志视图中的含义必须保持一致。

#### 场景: 用户按条件筛选日志
- **当** 用户输入时间范围、模型名、分组、请求 ID 或状态条件
- **那么** 系统必须返回符合条件的日志结果
- **并且** 在不同日志类型中保持一致的筛选语义

#### 场景: 用户从其他页面带筛选进入日志中心
- **当** 用户从总览页、分析页或模型页跳转到日志中心
- **那么** 系统必须自动带入对应筛选条件
- **并且** 允许用户继续调整这些条件

### 需求: 日志详情可追踪
客户门户必须为日志提供统一详情视图，展示时间、模型、消耗、计费来源、
状态与错误信息，并在可用时展示 request id 以便追踪。

#### 场景: 用户打开日志详情
- **当** 用户打开任意一条日志的详情
- **那么** 系统必须展示该记录的核心追踪信息
- **并且** 对失败记录展示明确的错误信息

#### 场景: 用户在详情中追踪问题
- **当** 日志记录存在 request id 或可关联的模型信息
- **那么** 系统必须展示可追踪的唯一标识或联动入口
- **并且** 允许用户继续跳转到相关模型或账单上下文
